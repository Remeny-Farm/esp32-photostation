# Upload protocol

This is the contract between an esp32-photostation device and its upload server. The firmware
(`firmware/station/src/hw/uploader.cpp`, `net.cpp`, `src/core/policy.cpp`) implements the client
side; `tools/mock_server.py` is a reference server for bench tests. A production server must
implement the three endpoints below with the same status semantics. Everything else (storage,
gallery, review queue) is the server's own business.

Example base URL throughout: `https://upload.example.com`. The station stores the base URL in NVS
(`url`) and appends the fixed paths under `/api/photostation/`.

## Transport

- HTTPS. The station verifies the certificate chain and the host name against the ESP32 core's
  built-in CA bundle. Self-signed certificates do not work; use a certificate from a public CA.
- `http://` is accepted only for local mocks. It sends the device key in clear text over the LAN,
  so use a throwaway key with the mock, never the production key.
- The station does not follow redirects. A 3xx response is treated as a retry (see the status
  table) and the heartbeat shows `upload_state: "redirect"`. The base URL must be the final host,
  with no `http` to `https` or `www` redirect in front of it.
- Timeouts on the station: 5 s TCP connect (over TLS this is also the write-stall limit), 15 s
  response wait, 15 s TLS handshake. A server that needs longer than that to answer a 1 MiB POST
  looks like a network error to the station.
- The station sets no `User-Agent`.

## Authentication

Every request carries:

| Header | Value |
|---|---|
| `Authorization` | `Bearer <device key>` |
| `X-Station-Id` | the station id, for example `ps-01` |
| `Content-Type` | `image/jpeg` or `application/json` |
| `Content-Length` | body length; the station never uses chunked encoding |

One key per station, generated by the server operator and entered on the station once over USB
(`set key`). The server should store only a hash of the key, allow revocation, and rate-limit per
station. A revoked or wrong key must answer `401` or `403`; the station then stops uploading until
it is rebooted or receives a new key, and the heartbeat shows `auth_stop`.

## Endpoints

### `POST /api/photostation/photo`

One photo. The body is the raw JPEG (not base64, not multipart).

Request headers in addition to the common ones:

| Header | Value |
|---|---|
| `X-Visit-Id` | the visit id; must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` |
| `X-Photo-N` | photo number in the visit, `1` to `5` |
| `X-Captured-At` | capture time, ISO-8601 UTC with `Z` (`2026-11-03T10:15:02Z`). Present only when the station knew the time; the station never sends an empty value. Missing header: store `captured_at = null`. |

Server checks, in the order the reference server applies them:

| Status | Error code | Condition |
|---|---|---|
| `401` | `unauthorized` | bad or revoked key |
| `415` | `unsupported_media_type` | `Content-Type` is not `image/jpeg` |
| `400` | `bad_request` | `X-Photo-N` not an integer 1-5, or `X-Visit-Id` does not match the pattern |
| `413` | `too_large` | body over 1 048 576 bytes |
| `422` | `not_jpeg` | body does not start with `FF D8` |

Success: `201` when the photo is new, `200` when `(visit_id, n)` was already stored. Both bodies
are `{"ok": true, "visit_id": "<id>", "n": <n>}`. Error bodies are
`{"ok": false, "error": "<code>"}`.

Photos are 1600x1200 JPEG at quality 10, typically 120-145 KB. The station never sends a file
over 1 MiB; such a file goes to `/bad` on the card without a request.

### `POST /api/photostation/visit`

The visit record, sent once per visit after all of that visit's photos. The body is the JSON of
[architecture.md section 5.5](architecture.md#55-visit-json):

- `station_id`, `visit_id`, `started_at`, `ended_at`, `time_synced`, `firmware`
- `photos[]`: `{n, captured_at, bytes, width, height}`
- `identification`: `decision` (`"tag"` or `"unknown"`), `tag_mac`, `tag_name`,
  `candidates[]` of `{mac, median, count, min, max}`, `threshold_dbm`, `margin_db`

The rules for times, `time_synced` and `null` values are in that section. `tag_mac` and every
`candidates[].mac` is the tag's BLE address, uppercase, colon separated (`AA:BB:CC:DD:EE:01`). For
the reference tag the address survives reboots and battery changes
([tag-protocol.md](tag-protocol.md#reference-tag-advertisement)), so it can serve as a unique key
on the server.

Checks: `400` when `visit_id` is missing or malformed or `photos` is not a list; `413` over
1 MiB; `422` when a listed photo has an `n` outside 1-5. Success: `201` first time, `200` on a
repeat. The response body is `{"ok": true, "visit_id": "<id>", "incomplete": <bool>}`, where
`incomplete` is true when the JSON lists a photo the server has not received. A repeat recomputes
it, so a later retry can show the gap closed.

The server should ignore unknown keys so that the firmware can add fields later. Firmware after
0.3.0 no longer sends `light_pwm`; a server must not require it.

### `POST /api/photostation/heartbeat`

Sent as soon as the uploader can reach the server after boot (configured, Wi-Fi up and, over
HTTPS, the clock set; about 6 s on a bench board), then every 5 minutes. Body is a JSON object;
the server answers `200` and should ignore unknown fields. Fields in firmware 0.3.0:

| Field | Type | Meaning |
|---|---|---|
| `station_id` | string | station id |
| `firmware` | string | firmware version (`0.3.0`) |
| `uptime_s` | integer | seconds since boot |
| `free_heap` | integer | free heap now (bytes) |
| `min_heap` | integer | lowest free heap since boot |
| `free_psram` | integer | free PSRAM (bytes) |
| `free_int` | integer | free internal RAM |
| `largest_int_block` | integer | largest free internal block now |
| `int_largest_min` | integer | running minimum of the largest free internal block since boot, sampled after each capture and inside each HTTP request while the TLS context is still allocated |
| `sd_ok`, `cam_ok` | boolean | SD card mounted, camera initialized |
| `sd_used_pct` | integer | card usage in percent |
| `queue_len` | integer | files waiting in `/q` |
| `bad_len` | integer | files in `/bad` |
| `wifi_rssi` | integer | Wi-Fi RSSI in dBm, `0` when down |
| `chip_temp_c` | number or `null` | internal chip temperature |
| `time_synced` | boolean | SNTP has set the clock |
| `last_visit_at` | string or `null` | ISO-8601 UTC of the last visit opening |
| `upload_state` | string | `idle`, `uploading`, `retry`, `auth_stop`, `no_wifi`, `no_time`, `no_config`, `redirect` |
| `pir_stuck` | boolean | the PIR level is being ignored after three forced closes in a row |
| `forced_closes` | integer | visits closed by the 10-minute cap since boot |

The heartbeat is the station's only supervision channel. A server should alert when a station has
not sent one for about 30 minutes, and keep the last heartbeat for display.

## Status handling on the station

`classify()` in `src/core/policy.cpp` maps the HTTP status (or a negative value on a network or
TLS error) to an action:

| Status | Meaning | Station action |
|---|---|---|
| `200`, `201` | stored, or already stored (idempotent repeat) | file moves to `/sent/<YYYYMMDD>/` |
| `400`, `413`, `415`, `422` | bad request; a retry will not help | file moves to `/bad/`; the heartbeat `bad_len` rises |
| `401`, `403` | wrong or revoked key | uploads stop until reboot or `set key` / `set url`; `upload_state` = `auth_stop` |
| `429`, `5xx`, `3xx`, `<= 0` (network error, timeout), anything else | temporary | retry with backoff `min(5000 * 2^n, 600000)` ms; `upload_state` = `retry` |

A successful request resets the backoff counter. After a retry the station starts the pass again
from the oldest file. A file whose local read fails three times in a row goes to `/bad` so that
one bad file cannot block the queue.

## Idempotency

- Photos are idempotent on `(visit_id, n)`; the visit record is idempotent on `visit_id`. A
  repeat returns `200` and the station counts it as sent. This is what makes retries after a
  timeout safe: the station cannot know whether the first attempt reached the server.
- The `visit_id` format is in [architecture.md section 5.4](architecture.md#54-sd-layout). The
  counter restarts at every boot; the boot number makes the unsynced form unique.

## Ordering

- The queue is sent oldest visit first (string order of the visit id), photos `1..n` in numeric
  order, then that visit's JSON last. The server therefore normally has every photo before it
  sees the record.
- Uploads never start while a visit is open. A PIR edge lets the request in flight finish and
  blocks new ones. Uploads of a visit begin a few seconds after it closes.
- If the station reboots during a visit (power loss, watchdog, OTA), the photos already on the
  card are uploaded later, but the visit JSON never arrives. The server should not wait for it
  forever: after a timeout, close the visit as incomplete and put it in a review queue.
- If the JSON arrives before a photo it lists (a move failure on the card, a manual retry), the
  server should store the visit as `incomplete` and attach the photo when it comes.

## Mock-only endpoint

`POST /__mode` with body `{"fail": N}` makes the reference server answer `503` to the next `N`
device requests. It has no authentication and exists only to test the retry path. A production
server must not expose it.

## Server-side advice

- Store the key hash, not the key. Rate-limit per station id.
- Keep photos under a key like `<station>/<visit>/<n>.jpg`; keep the visit JSON next to them.
- Selection v1: the largest JPEG of a visit is a cheap proxy for the sharpest one at a fixed
  quality setting.
- Publish automatically only when `decision` is `"tag"` and the tag is mapped to an animal.
  `unknown` visits and unmapped tags go to a review queue where a person assigns or discards
  them. Keep a tag-to-animal mapping with validity dates, because a tag can move to another
  animal later.
- Keep the `candidates` arrays. They are the data you need to tune `threshold_dbm` and
  `margin_db` for your box.
